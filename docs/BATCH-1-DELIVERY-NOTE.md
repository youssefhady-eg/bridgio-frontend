## 2. Data layer — no contract change

Every call goes through `src/api/`; no component calls `fetch`. No signature in `src/api/contract.ts` was added or changed. Every endpoint used is already marked **PROPOSED** in the contract.

| Screen | Adapter calls | Contract status |
| --- | --- | --- |
| Question bank | `tests.listForTeacher` → `questions.listForTest` per test | both PROPOSED |
| Material library (list) | `materials.listForTeacher` → `classrooms.listForTeacher` → `classrooms.get` per class (for unit names) | all PROPOSED |
| Material library (add) | `materials.create` | PROPOSED |
| Material library (expand) | `materials.get` | PROPOSED |
| Material library (delete) | `materials.delete` | PROPOSED |

**Composed, not invented.** The contract exposes `questions.listForTest` only, so the bank reads the teacher's tests and then each test's questions (one call per test — an honest N+1). A future PROPOSED `questions.listForTeacher` would collapse it; it was **not** added in this batch because the composed query needs no contract change. Likewise the library reads unit names through `classrooms.get`, which already exists.

**Teacher-only, enforced twice.** `questions.listForTest` carries `correctOptionId` and the mock rejects a non-teacher actor. On top of that, the bank wrapper does not run the query unless the session role is teacher, and shows a no-session note otherwise. Student screens keep using `questions.listForStudentTest`; the student flow is untouched.

**Upload gap, stated not faked.** `materials.create` accepts `text` and `link` only in the UI. PDF/image are shown as an integration gap; the screen says upload is not available yet and records metadata only. There is no fake file input, no fake progress, and no fake storage. The mock marks `text` and `link` as `ready` and would mark a binary kind `processing`; the UI never sends a binary kind.

**No scores, no marking.** The bank shows the authoring reference answer (`correctOptionId`, already in the contract); no attempt score, percentage or grade is produced or displayed anywhere in this batch.

**Seed data.** 3 tests / 6 questions (derivatives ×3, integration draft ×1, physics ×2) and 2 text materials. The two seeded materials are each a test's source, so deleting either returns `CONFLICT` — that is real mock behaviour, not a UI invention.

## 5. Deviations and open items

1. **Figma T10C / T13C frames were not available in this session.** Both screens are built from the current BRIDGIO design system (existing `PageHero`, `EmptyNote`, `StatusChip`, `QuestionCard`, `filter-bar` patterns, locked tokens) rather than a traced frame. This is the one visual deviation; re-check both screens against the frames when they are supplied.
2. **The question bank is browse-only in Batch 1.** There is no "copy into a test" or reuse flow, and questions are edited from their test's builder (the screen says so). Reuse was not in the batch scope.
3. **Composed N+1.** The bank issues one `questions.listForTest` per test. Fine for the seed data; if a real teacher has many tests a PROPOSED `questions.listForTeacher` should replace it.
4. **Collapsed label visibility is immediate.** Labels use the existing clip-based visually-hidden pattern (so each control keeps its accessible name); the rail geometry animates, the label text does not fade. Recorded as a known, deliberate trade-off, not a layout jump.
5. **390 px screenshots carry a desktop scrollbar.** Captured in Brave at a 390 px viewport, so a ~15 px scrollbar sits inside the layout; a real phone has none. The drawer-open capture shows the drawer flush to the layout viewport for the same reason.
6. **Delete of a seeded material always conflicts** because each seeded material is a test's source in the mock. Use a newly created material to see a successful delete.
